# Webhook Delivery Contract

## Acceptance and deadline

Orbit 3.0 retries eligible failed webhook deliveries for 72 hours from the first attempt. Network failures, HTTP 408, HTTP 429 and HTTP 5xx are retryable. HTTP 400, HTTP 401, HTTP 403, HTTP 404 and HTTP 410 terminate delivery immediately. HTTP 2xx acknowledges acceptance. Each HTTP request times out after 10 seconds.

A receiver should authenticate the request, persist the event and then acknowledge it. Returning success before durable persistence can lose a business action when the receiving process crashes. Returning success only after a slow downstream workflow can cause needless retries. Put the long-running action behind the receiver queue. Delivery history records the receiver status, but it cannot prove that the receiver completed its business action.

## Signing and scheduling

Verify X-Orbit-Signature with HMAC-SHA256 over the raw request bytes before JSON decoding. Whitespace normalization changes the signed bytes. The initial retry delays are 1, 5, 15, 60 minutes, then hourly, with 20 percent jitter, until the deadline. Delivery is at least once. Do not use a timestamp as a unique event key.

A receiver clock that is wrong can make diagnostic logs appear out of order. Compare timestamps in UTC and keep the delivery identifier when recording a failure. During credential rotation allow only the explicitly configured overlapping secrets. Never accept an unsigned callback as a temporary workaround.

## Receiver persistence

A duplicate can follow a successful receiver transaction if the acknowledgment is lost. The sender cannot distinguish that situation from a failed receiver. Store the identifier from X-Orbit-Delivery-ID with the committed business action. The deduplication record must survive a receiver restart. An in-memory set is insufficient when several receiver processes share the same queue.

The delivery history and receiver log serve different purposes. History shows attempts, while the receiver log connects a delivery to a local action. Keep these identifiers separate from a device name, which can change. A replay must preserve the delivery identifier when it represents the same delivery.

## Deduplication lifetime

Retain receiver deduplication records for 96 hours after first acceptance. This receiver-side lifetime deliberately exceeds the Orbit 3.0 sender retry window. Expiring the record when the application task finishes is too early: a delayed duplicate could execute the same action again.

Use a uniqueness constraint that includes the subscription identifier and delivery identifier. If two consumers intentionally process the same event for different business purposes, each consumer owns its own deduplication boundary. Do not share one global processed flag across unrelated consumers.

## Reconcile a connection failure

Consider a receiver that authenticates a request, commits a local work item and then loses its connection before the sender receives the success response. The sender has evidence of a failed attempt, while the receiver has evidence of a committed action. Neither record is necessarily wrong. The receiver must be able to map the repeated delivery to the existing action without asking the sender to prove that the first action happened.

Keep the acceptance transaction small. Store the original delivery identity, subscription identity and a local action reference together. The slow work belongs behind that transaction. If an external system performs the business action, record a state that can distinguish queued, dispatched and reconciled. A process restart between dispatch and reconciliation needs a different repair from a request that never passed signature verification.

When collecting logs, compare attempt identifiers, delivery identifiers and local action identifiers in separate columns. One delivery can have several attempts. One attempt can fail before a local action exists. A report that labels all three identifiers event ID discards the relationships needed to reconstruct the failure.

## Replay review

A manual replay should have an operator, a reason and a defined set of deliveries. Do not replay every request from an entire day solely because one downstream action is missing. First determine whether the action was never committed, was committed but not completed, or completed with an acknowledgment that was lost. Replaying the wrong layer can repeat a successful business operation.

Before authorizing the replay, confirm that the receiver persistence is still available. If its local record was removed too early, a receiver can no longer distinguish a duplicate from a fresh action using that record alone. Reconcile against the business system before recreating work. A new HTTP request cannot repair an ambiguous business history automatically.

After the replay, compare the selected delivery set with the repaired local actions. Save a compact reconciliation record with references rather than copying full payloads into a broadly readable incident report. Report unresolved cases individually; a lower error count does not establish that every missing action was recovered.
